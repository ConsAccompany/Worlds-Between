# M8 探索角色素材入库检查清单（设计稿）

**状态：仅为设计，尚未实现。** 本文没有改动任何代码、清单或注册表，也不批准任何素材。所列自动检查是对现有构建脚本的扩展建议，目前大多尚不存在（见末节「现状差距」）。上位标准见[高精度探索角色制作标准](rpg-2-star-ocean-the-second_scifi-city_premium-exploration-production-standard_m8-draft_20261014-153400-481ae2c9.md)。

已定：城市探索角色显示高度 48 逻辑像素（用户已批准）。未定：高精度美术、方向保真、动画、批量制作。旧 32×48 原生帧（锚点 `[16, 44]`）是功能占位，不能按本清单转为正式素材。

## 分工

| 角色 | 负责 |
|---|---|
| ChatGPT | 生成图像、桌面/浏览器操作、视觉初审 |
| 用户 | 最终美术判断；唯一可以把任何项目标为「用户美术验收」的人 |
| Claude Code | 自动元数据检查、清单与注册表脚本、文档；不做美术判断 |

自动检查通过只说明元数据和文件合格，**不等于**视觉合格，也不得改写任何 `approval` / `review_status` 字段为通过。

## 1. 范围

- 注册表（`game/data/character-visuals/…_character-visual-registry_m8-v01_…-2a5d1b3c.json`）共 **52 个视觉变体**：主角男、主角女，加 50 名同伴。按角色计为 51 人（主角算一人，含男女两种可选外观）。
- 构建脚本当前硬性校验：总数 52、来源立绘 `approved` 9 / `concept` 43、`visual_id` 不重复、来源立绘文件存在。入库不得改变这些总数，除非用户另行改动名册。
- 每个变体的探索帧数**尚未确定**，任何数字都不是已批准的最低标准：
  - 现有运行时布局为四方向待机各 1 张 + 行走各 4 相位 = **20 张**；这是占位帧的现状，不是正式素材要求。
  - [可行性评审](rpg-2-star-ocean-the-second_exploration-walk-pipeline_feasibility-review_m8-v01_20261014-163221-c4e19a7d.md)提议先用一个角色做质量试点：四方向 ×（待机 4 + 行走 8）= **48 张**。这只是试点提案。
  - 正式生产帧数须依据试点证据，并经用户明确批准后才确定。
  - 不论最终取值，每份清单都必须显式声明各方向、各动作的帧数（见第 3 节），校验脚本按声明值检查，不硬编码 20 或 48。
- 所有帧都是独立 PNG 文件。战斗侧视另有规格，不在本清单内。
- 正式探索角色当前为 **0/52**。

## 2. 图像分离与命名

- **一图一文件**：每个方向、动作、相位单独一张透明 PNG。不接受拼图、精灵表、多方向合图、带背景或带阴影的图。阴影由引擎另外绘制。
- 原始高精度概念图与游戏帧分开存放、分开登记；概念图不能直接当游戏帧入库。
- 文件名格式（项目代号在前，时间戳和唯一 ID 在后）：

  ```
  rpg-2-star-ocean-the-second_<visual-id>_<种类>-<动作>-<方向>[-phase-NN]_<里程碑-版本>_<YYYYMMDD-HHMMSS>-<8位十六进制>.png
  ```

  - `<visual-id>` 必须与注册表 `visual_id` 完全一致（短横线小写，如 `liang-xu`，不能写成 `liang_xu`）。
  - `<方向>` 只能取 `south` / `west` / `north` / `east`。
  - 相位两位补零，从 `phase-01` 连续编号到清单为该方向、该动作声明的帧数为止（例如现有 4 相位行走到 `phase-04`，试点 8 相位行走到 `phase-08`）。只有一帧的待机可不带相位；多帧待机同样编号。
  - 8 位 ID 在全仓库唯一；重新生成的图用新时间戳和新 ID，不覆盖旧文件。

## 3. 清单字段（每张图一条）

现有两份高精度概念清单字段不统一：主角清单只有裸文件名 `file`，没有哈希、alpha 包围盒和脚点；梁序清单有 `source_png`、`sha256`、`source_size`、`alpha_64_bounds_inclusive`、`foot_anchor_source_pixels`。入库以后者的文件与哈希字段为基准；但其中的包围盒和脚点是静态比例实验的逐图测量（见第 7 节），生产帧改用固定格子与锚点。每条至少包含：

| 字段 | 说明 |
|---|---|
| `visual_id` | 与注册表一致 |
| `action` / `direction` / `phase` | 单帧待机相位记为 0；多帧动作从 1 起 |
| `path` | 仓库相对路径 |
| `sha256` | 统一大小写 |
| `source_size` | 像素宽高 |
| `alpha_bounds_inclusive` + `alpha_threshold` | 记录阈值，不要只写在字段名里；只作报告与比对，不用于算缩放或锚点 |
| `contact_points` | 该帧着地的脚及其在格子内的坐标；只作步态记录，不用于重新缩放或重新居中躯干 |
| `west_authoring` | `independent` 或 `mirrored_east` |
| `identity_reference` | 来源立绘路径 |
| `stage` | 只记录制作阶段，不写批准 |
| `review_receipt` | 实机截图及回执路径（如有） |

此外，每份清单在顶层须有一个 `frame_counts` 字段，显式声明每个方向、每个动作的帧数（如 `{"walk": {"south": 8, …}, "idle": {"south": 4, …}}`）。缺少该字段视为检查失败，脚本不得自行假定默认值。

同样在顶层，每个视觉变体只声明一次：`master`（固定分辨率母版的路径与哈希）、`scale`（由母版定出的唯一缩放）、`cell_size`（所有帧共用的画布格子）、`ground_pin`（格子内的地面锚点）。逐帧字段不得再带各自的缩放或锚点。数值待试点决定；[可行性评审](rpg-2-star-ocean-the-second_exploration-walk-pipeline_feasibility-review_m8-v01_20261014-163221-c4e19a7d.md)的试点提案为格子 80×112、锚点 (40,104)。缺少任一字段视为检查失败。

批准状态不放在逐帧字段里，统一记在注册表的状态字段（见第 9 节）。

## 5. 四方向

- 必须有 `south`、`west`、`north`、`east` 四个方向，顺序以注册表 `direction_order` 为准。
- 西向默认要求独立绘制。东向镜像只可用于实验，必须在 `west_authoring` 标为 `mirrored_east`，并须用户明确接受才能留用（角色有不对称配件、侧发或包时尤其要注意）。
- 方向保真由人工判断。已记录的问题可作参考：梁序东向头部为侧面而躯干仍偏四分之三；北向头部略转、露出耳朵。
- 侧面、背面因姿态自然变窄是正常的；身高、头部体量、肩宽、衣摆体积要保持连贯，不靠逐张拉宽。

## 6. 行走连贯

- 每方向的行走相位数按清单 `frame_counts` 声明（现有占位为 4，试点提议 8），全部相位为一个循环，最后一相位应能自然接回相位 1。
- 自动：各相位画布等于顶层 `cell_size`、锚点等于顶层 `ground_pin`；躯干在格子内水平位置不变，只按步态上下起伏；alpha 包围盒高度变化在步态起伏范围内（阈值待定，只报告）；接触点只按步态规律变化。
- 人工：五官、发束、衣扣、包、武器、总轮廓在帧间一致；脚底接触与上下起伏符合步态；发尾、围巾摆动合理；转向瞬间体量不跳变。
- 只看单张迈步图不能证明循环稳定，必须看实机短动画。

## 7. 固定格子、地面锚点与接触点

- **历史（静态比例实验）**：用户批准 48 逻辑像素时依据的截图里，静态方向概念图是逐张按自身强可见 alpha 包围盒独立缩放、鞋底对齐同一地面脚点的。这只用于比较显示高度，不适用于动画帧：逐帧独立缩放和对齐会造成身体大小与左右位置跳动（见可行性评审 C2）。
- **生产帧**：每个变体一张固定分辨率母版，缩放只由母版定一次；该变体所有方向、动作、帧共用同一 `scale`、`cell_size` 与 `ground_pin`。引擎以锚点为节点原点。透明留白、发型和背包不改变格子与锚点。
- 每帧记录 `contact_points` 供步态检查；不得据此重新缩放或重新居中躯干。
- 自动：每帧尺寸、缩放、锚点与清单顶层声明一致；接触点在格子范围内、与清单一致、且只按步态规律变化。不从 alpha 包围盒重算缩放或锚点。引擎内支撑脚是否打滑由实机捕获检查。
- 人工：在城市实机截图中确认角色踩在地面上，不浮不陷；阴影位置与脚对齐。

## 8. Alpha

- 背景必须完全透明，不允许残留底色、棋盘格或描边框。
- 自动：报告 alpha 阈值下的包围盒与低透明边缘像素数量；检测四角是否完全透明。
- 人工：分别在亮地面和暗地面上检查晕圈与半透明毛边。三份梁序概念图都已记录有低透明毛边，须先处理才能用于生产。

## 9. 注册表状态门槛

与 Game Bible 的四个阶段对应。每一级都须前一级已通过；**只有用户可以开最后一道门**。

| 阶段 | 进入条件 | 谁来推进 |
|---|---|---|
| 1 已生成概念 | 独立 PNG 已入库，清单字段完整，第 4 节自动项全部通过 | Claude Code 跑脚本记录 |
| 2 已在实机技术复核 | 有 1280×720、`canvas_items`、48 逻辑像素的城市实机截图和回执 | ChatGPT 截图，Claude Code 登记路径 |
| 3 已接入可玩 | 已接入可玩场景，四方向待机与行走可在游戏中切换 | Claude Code 实现，需有运行证据 |
| 4 用户美术验收 | 用户逐项确认身份、方向、动画、alpha；须有书面回执文件 | **仅用户** |

规则：

- 自动检查失败时，状态停在原阶段，不得手动跳级。
- 文件哈希变化（重画、修图）时，该变体退回阶段 1 重新检查，既有批准作废。
- 用户批准写成单独的回执文件（日期、范围、依据截图路径），注册表只引用它，不在脚本里硬编码「approved」。
- **批量门槛**：须先有一个角色的四方向待机与行走达到阶段 4，并且用户已根据试点证据明确批准正式生产帧数，才能开始批量制作其余角色。

## 10. 现状差距（只记录，本次未改）

- 注册表构建脚本未检查：文件命名、`sha256`、alpha、格子、锚点、接触点、显示高度、西向镜像。
- 现有概念清单的包围盒与脚点来自静态比例实验的逐图归一化；所有清单都还没有 `master`、`scale`、`cell_size`、`ground_pin`、`contact_points` 字段。
- 帧数靠硬编码区分（`protagonist-male`、`protagonist-female`、`liang-xu` 为 19 帧，`zhao-ling`、`ji-cheng` 为 20 帧），没有从清单字段读取；运动注册表构建脚本也一样。现有清单也都还没有 `frame_counts` 字段。
- `milo` 与 `jiang-lan` 已有原生探索清单，但两个构建脚本都没有登记。
- 梁序动画清单 `character_id` 写作 `liang_xu`，与注册表 `liang-xu` 不一致。
- 注册表把男女主探索标为 `four_direction_native_walk_integrated`，指的是 32×48 占位帧，不是高精度素材。
- 主角高精度概念清单仍把 48 写成 `provisional_visible_height_logical_px`，未反映用户已批准此显示高度；该清单也缺哈希、包围盒和脚点。
