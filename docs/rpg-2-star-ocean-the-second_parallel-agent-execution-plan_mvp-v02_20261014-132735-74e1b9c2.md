> 准备日期：2026-10-14（美国东部）。**仅做准备；尚未启动代理或执行下面的开发任务。**用户说“go”后，由当前聊天作为统筹者，同时启动三位子代理。基线为 `main` 上的游戏圣经与 [完整交接](rpg-2-star-ocean-the-second_project-handoff_full-chat_v01_20261013-234135-a6e29f3c.md)；开工时先重新核对 Git 状态、最新 `main` 与现行 [MVP v0.2](../outputs/rpg-2-star-ocean-the-second_mvp-implementation-plan_visual-first_v02_20261013-230524-29cf8a61.md)。

## 并行目标与不可变边界

第一轮以一张**可真正走动的科技城市场景**为视觉和玩法样板；同时建立角色视觉资产的可重复生产规范，并独立完善 M7/M8 验证。已有远端 `codex/city-cutout-foot-anchors`（`02e00d1`）和其后续 `codex/city-walkable-boundaries`（`8a52e9d`）完成角色足底定位、基础障碍、存档位置恢复和对应自动测试；A 从后续分支派生，不重复实现这两项。完整 MVP 仍要求主角男女＋50 位伙伴共 **52 个视觉版本**有游戏内展示和四方向探索形象、科技区 **11 处场景**达到目标品质；首个可玩内容仍限科技区。第一轮样板不是缩小终点。M7 的真人 25–35 分钟两顺序试玩仍由真人完成，代理不能制造或代替真人回执。M8 城市视觉方向、角色样板与资产勾选仍需基于运行画面审核。

同一时刻运行 **3 位子代理＋当前统筹者**。不创建三个新的用户聊天；子代理在此聊天内汇报。每人使用自己的 Git worktree 与分支，避免共用 Git index。每人只编辑拥有的文件；跨范围发现以报告发给统筹者。代理提交到自己的分支，统筹者审查并整合到 `main`，再统一更新游戏圣经、资产清单、`docs/progress.md`，最后推送到 `origin/main`。不可将自动化检查与静态图误写成真人试玩或视觉验收。

### 代理 A 的首轮交付与验收

1. 先读[交接](rpg-2-star-ocean-the-second_project-handoff_full-chat_v01_20261013-234135-a6e29f3c.md)、MVP v0.2、现有城市分支的两份 review 与当前 `scifi_exploration_area.gd`。保留原有三地入口、角色招募、调查点、行走边界和存档语义；不重做足底定位或障碍描绘。
2. 以选定的科技城市 v02 背景、主角男女与梁序 cutout 为现有起点，明确最小可走区域与物件遮挡。主角在正常窗口中应看起来站在地面上；热点应有可辨识视觉标记，不能藏在不可走位置。
3. 交付一组真实 Godot 运行截图：至少主角男女各一张、梁序可见和招募后不可见各一张、HUD 与一个交互点各一张。每个截图是独立文件，附简短审查记录。截图不等于通过画质最终门槛。
4. 验证城市入口、出口、报告、勘察室、外勤站、两条痕迹、梁序招募、存档回城；若某项失败，先修复再提交。保留其余科技区场景原有功能。
5. 提交可复现变更及确切测试结果，列出仍待用户决定的视觉方向、技术约束与进一步分层需求。

1. 盘点 52 个角色视觉版本，与人物圣经／角色图 manifest 按稳定 ID 对齐。明确 **9 张已批准来源画像**与 **43 张仍待审概念稿**；不能擅自把“文件存在”改成“通过”。整理重复发型／轮廓风险和缺失图，但不更改已经批准的角色身份。

## 启动与整合协议

**用户说“go”时：**

1. 统筹者确认 `main` 干净、`origin/main` 一致，读[交接](rpg-2-star-ocean-the-second_project-handoff_full-chat_v01_20261013-234135-a6e29f3c.md)与本计划；确认 A 从现有城市后续分支、B/C 从当前 `main` 派生，准确记录各自起点。若已有用户新改动，先保留并重新划定所有权。
2. **同时**用 `collaboration.spawn_agent` 启动 A、B、C，将各自目录、所有权、上述交付、先验规则、需要提交分支和直接汇报要求放入任务消息。三个代理都应继承本聊天的完整上下文。不得在用户说“go”之前调用启动工具。
3. 统筹者在代理运行时独立做非冲突工作：核对源画像及城市运行验收标准、准备分支审查；约每 60 秒给用户可验证的进度，而不是只等待。若代理提出跨范围阻塞，统筹者协调接口。
4. 代理先交付可审查的较小成果，不能为了填满清单生成未经检验的大批素材。各自在独立分支提交，汇报 commit ID、改动文件、检查结果、未完成项。不得自行推 `main`，不得替用户批准素材。
5. 统筹者逐分支查看 diff，先将现有城市分支及 A 的后续改动按顺序整合，再整合 C 的验证、B 的新资产／映射；处理冲突并运行 Godot 导入、M7 回归与真实画面检查。保留自动测试与人工视觉评审的区别。
6. 统筹者更新进度、资产清单及 GitHub 来源的云端 Game Bible 跟踪器数据，仅将通过各自用途审查的项目勾选；经确认的变更推送到 GitHub。若样板需要用户审美决定，提供引擎截图、差异、具体决定点，然后继续可独立进行的工作。两条完整真人试玩仍须真实玩家执行。

## 风险控制与停点

- **资源竞争：** `game/.godot/` 在每个 worktree 内独立；Godot 的 `user://` 目录可能跨 worktree 共用，测试须隔离路径或协调运行。图像生成长耗时，与引擎测试并行最有效。
- **美术批准：** 当前城市预览只是候选；A 可以改进样板，B 可以制订角色规格，但 52 人全量和 11 场景批量制作要以明确运行画面样板为基线。未获得批准时可继续做登记、规范与工具，不能默默把同风格扩充标成通过。
- **Git 所有权：** 不共用主 checkout 的 index；代理分支不能改对方专属文件，也不能直接推 `origin/main`。跨分支接口由统筹者整合。
- **命名：** 每张生成图独立保存；所有新素材、截图、manifest 按用户给出的描述性项目文件名规则命名。
- **完成定义：** 第一轮三代理任务完成只意味着“城市可玩样板＋角色生产规范和方向样板＋可信验证准备”，**不等于完整 MVP、M8 视觉验收或真人试玩完成**。
